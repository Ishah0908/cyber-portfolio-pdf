IAM/PAM Break-Glass Playbook

Published December 9, 2025 · 18 min read

Emergency access is necessary, but unmanaged break-glass accounts become attacker shortcuts. Treat emergency credentials as controlled explosives: sealed, logged, and time-bound. A poorly managed break-glass account that gets compromised is a direct path to complete infrastructure takeover during the chaos of an active incident.

The Break-Glass Problem

Break-glass (or break-emergency) accounts exist for one reason: when normal access controls fail during an incident, you need a way in that doesn't depend on IdP availability, MFA systems, or conditional access engines. But this creates a paradox: the account that provides emergency access is also the account that, if compromised, bypasses all your defenses.

Most organizations handle this poorly. They create one or two break-glass accounts, write the credentials down (or worse, keep them in an old wiki page), and check the annual box that says "we have emergency access." The reality: if that account ever gets used, nobody knows, nobody logs it properly, and the credentials are often more than a year old.

Architectural Principles

Break-glass accounts must be:

  • Physically separated: Stored in a physical safe, vault, or HSM. Not in Okta. Not in your password manager.
  • Multi-person required: No one person can unilaterally activate them. Require dual keys or escrow.
  • Logged loudly: Every activation triggers alerts to multiple teams and creates an audit trail that can't be deleted.
  • Time-bounded: If you activate credentials, they expire in hours, not days. New ones for each incident.
  • Post-incident reviewed: Within 24 hours, leadership reviews why it was needed and what was accessed.

Implementation Strategy

On-Premises / Hybrid

Maintain 2-4 break-glass Domain Admin accounts in Active Directory that:

  • Have no logon rights except from a secured physical device.
  • Are disabled by default. Enabling them creates an event in Sysmon and forwards to a SIEM trigger.
  • Have all password-reset history disabled so compromised credentials can't be traced backward.
  • Are subject to session recording (Deception Monkey, Privilege Manager recording, or appliance-level logging).

Cloud (AWS / Azure / GCP)

Create dedicated break-glass IAM users or roles that: 

# AWS Example: Break-Glass User with Inline Policy
aws iam create-user --user-name break-glass-incident-responder-a

# Attach a policy that grants minimal but sufficient access
aws iam put-user-policy --user-name break-glass-incident-responder-a \
  --policy-name EmergencyAdminPolicy \
  --policy-document file://emergency-policy.json

# Lock it down with a Service Control Policy (SCP) that only allows activation
# during business hours and from a specific IP range
# Store the access keys in AWS Secrets Manager with automatic rotation disabled

# Enable CloudTrail logging on the account and alerts on ANY break-glass usage
aws cloudtrail put-event-selectors --trail-name management-events \
  --event-selectors '{ "ReadWriteType": "All", "IncludeManagementEvents": true }'

Kubernetes / Container Infrastructure

Create a break-glass service account that:

  • Has cluster-admin role binding but is disabled by default via RBAC deny policy.
  • Can only be activated via a manual admission webhook that logs to an immutable audit destination.
  • Gets a unique token per incident (short-lived, rotated hourly).
  • Actions are captured in the API audit log with PII redaction disabled for incident investigation.

Activation Workflow

When an incident requires break-glass access:

  1. Page the duty manager and one other approver. Both must approve via out-of-band channels (phone, SMS, not Slack).
  2. Create a ticket in your incident management system with: incident ID, approvers, time of activation, intended access scope.
  3. Physically unlock the safe (if on-prem) or retrieve the credentials from AWS Secrets Manager (with MFA and approval logs).
  4. Generate a new password/key for this use only. Do not use a year-old key.
  5. Activate the account. This should trigger alerts immediately to your SOC.
  6. Enable session recording before any actions. If it's Kubernetes, ensure audit logging is on.
  7. Perform only the minimum actions required to resolve the incident. No browsing, no "while I'm in here" exploration.
  8. Disable the account the moment the incident is over. Don't wait for end-of-shift or end-of-incident meeting.
  9. Rotate all temporary keys/passwords immediately. Destroy the old ones, don't vault them.
  10. Within 24 hours, hold a post-incident review. Was the emergency access actually needed? Could a normal elevated permission have handled it? Did anything unexpected happen?

Audit and Verification Commands

Linux / On-Premises

# Verify break-glass accounts exist but are disabled
getent passwd | grep break-glass

# Check account is locked
passwd -S break-glass-account-1

# Verify no interactive login allowed in /etc/security/access.conf or PAM
grep -r "break-glass" /etc/pam.d/

# Review all invocations via sudo logs
journalctl -u sudo --all --lines=500 | grep break-glass

# Audit trail (if using auditd)
sudo ausearch -k break-glass-activation -ts recent

Cloud (AWS)

# List all break-glass users
aws iam list-users --query 'Users[?contains(UserName, `break-glass`)]'

# Check access keys attached (should be none or rotated regularly)
aws iam list-access-keys --user-name break-glass-incident-responder-a

# Pull CloudTrail events for any break-glass usage
aws cloudtrail lookup-events \
  --lookup-attributes AttributeKey=Username,AttributeValue=break-glass-incident-responder-a \
  --start-time 2026-01-01T00:00:00Z \
  --query 'Events[*].[EventTime,EventName,Username,CloudTrailEvent]' \
  --output table

Azure

# List break-glass accounts in Azure AD
az ad user list --filter "displayName eq 'Break Glass Incident Responder A'" \
  --query '[].{id:id,userPrincipalName:userPrincipalName,accountEnabled:accountEnabled}'

# Check for any sign-in events
az ad audit sign-in-logs list \
  --filter "userPrincipalName eq 'breakglass-a@company.onmicrosoft.com'" \
  --query '[].{createdDateTime:createdDateTime,status:status,ipAddress:ipAddress}'

# Verify MFA is enforced on the account
az ad user show --id breakglass-a@company.onmicrosoft.com | jq '.strongAuthenticationRequirements'

What Happens When Break-Glass Gets Compromised

If you discover a break-glass account was used by an attacker (not a legitimate incident responder), you're in a recovery scenario. Immediate actions:

  • Assume full infrastructure compromise. Every system that account can reach has been potentially accessed.
  • Force a password reset on every account that shares the IdP or domain. The attacker may have harvested credentials during their time in the system.
  • Revoke all active sessions and tokens. Don't just expire them; revoke them immediately.
  • Begin forensic analysis of that account's CloudTrail / audit logs. What did it actually do? When? From where?
  • Check for privilege escalation chains. Did the attacker use break-glass to grant themselves persistent access through a backdoor?

The Honest Truth

Most break-glass implementations fail not because the design is bad, but because:

  • The credentials are too easy to find.
  • Nobody actually tests the activation process until an incident happens.
  • Logging is incomplete or gets deleted in a purge.
  • The organization treats break-glass as a "just in case" thing and never maintains it.

If you implement break-glass, own it. Test the activation every quarter. Review the logs monthly. Rotate the credentials annually. And if it's ever used, investigate it like you're investigating a breach—because until you prove otherwise, it might be one.
