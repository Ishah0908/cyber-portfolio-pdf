Hardening Multi-Cloud Without Grinding Delivery to a Halt

AWS, Azure, and GCP, the way they actually look after three years of teams shipping fast: drifted, over-permissioned, and mostly fine until the one bucket that wasn't. Here is what I lock down first and why.

// 01

Where cloud breaches actually start

Almost none of the cloud incidents I have worked started with a clever exploit. They started with a misconfiguration and an over-broad identity. A public storage bucket. A role with *:* that someone created "just to unblock the demo" in 2023 and never tightened. A leaked access key in a git history. The attacker did not break in so much as walk through a door that was propped open.

So this handbook does not chase exotic threats. It hardens the three things that show up in the post-mortems over and over: identity blast radius, configuration drift, and exposed secrets. Get those right across all three clouds and you have closed the doors that matter most.

Framing that helps In on-prem you defend a network. In cloud you defend an API. Every resource, every action, every deletion is an authenticated API call. That means your control plane logs are your security camera, and your IAM policy is your lock. Treat both accordingly.
// 02

Identity boundaries first, always

The fastest risk reduction in any cloud estate is shrinking what identities can do. Not adding tools. Shrinking permissions. Start by finding the roles that can do anything, because those are your real attack surface.

aws // find IAM policies granting wildcard admin
$ aws iam list-policies --scope Local --query \
  'Policies[].Arn' --output text | tr '\t' '\n' | while read arn; do
    ver=$(aws iam get-policy --policy-arn "$arn" \
      --query 'Policy.DefaultVersionId' --output text)
    doc=$(aws iam get-policy-version --policy-arn "$arn" \
      --version-id "$ver" --query 'PolicyVersion.Document' --output json)
    echo "$doc" | grep -q '"Action": *"\*"' && echo "WILDCARD: $arn"
  done
WILDCARD: arn:aws:iam::1234:policy/demo-unblock-2023
WILDCARD: arn:aws:iam::1234:policy/ci-deploy-temp
# every line here is a role that owns your account if stolen

Azure and GCP have the same disease with different names. The pattern is identical: enumerate, find the over-broad grant, replace it with least privilege scoped to what the workload actually calls.

azure + gcp // surface broad role assignments
$ # Azure: who holds Owner or Contributor at subscription scope
$ az role assignment list --all \
  --query "[?roleDefinitionName=='Owner'].{p:principalName,s:scope}" -o table
PrincipalName              Scope
svc-legacy-etl@corp        /subscriptions/8f2...    # service acct as Owner

$ # GCP: project-level primitive roles (owner/editor) are a smell
$ gcloud projects get-iam-policy prod-app \
  --flatten="bindings[].members" \
  --filter="bindings.role:roles/owner OR bindings.role:roles/editor" \
  --format="table(bindings.role, bindings.members)"
roles/editor   serviceAccount:deploy@prod-app.iam...
The 10:1 problem Non-human identities (service accounts, workload identities, CI tokens) outnumber humans roughly ten to one in mature cloud estates, and they are the ones with standing broad access. A human with too much power at least sleeps. A leaked service account key works 24/7. Rotate them, scope them, and prefer short-lived workload identity federation over long-lived keys everywhere you can.
// 03

Guardrails over gates

A gate stops people at deploy time and makes them hate you. A guardrail lets them move freely inside a safe boundary and only stops the genuinely dangerous thing. Prevention beats detection here: a policy that makes it impossible to create a public bucket is worth more than an alert that one appeared.

Put the hard boundaries at the org level where no single team can override them, then scan infrastructure-as-code before merge so problems never reach an account.

aws // org-level SCP: deny disabling of guardrails
{
  "Sid": "DenyTurningOffSecurity",
  "Effect": "Deny",
  "Action": [
    "cloudtrail:StopLogging",
    "guardduty:DeleteDetector",
    "config:DeleteConfigurationRecorder",
    "s3:PutBucketPublicAccessBlock"
  ],
  "Resource": "*"
}
# now no account in the org can blind your logging or open a bucket
scan IaC before it ever deploys
$ checkov -d ./terraform --compact --quiet
terraform scan results:
Passed checks: 142  Failed checks: 3
FAILED  CKV_AWS_18  s3 bucket has no access logging  aws_s3_bucket.assets
FAILED  CKV_AWS_20  s3 bucket allows public read       aws_s3_bucket.assets
$ # wire this as a required CI check; a red here blocks the merge

CNAPP and the noise problem

A cloud-native application protection platform will, on day one, hand you ten thousand findings and a feeling of despair. The platform is not the hard part. The hard part is turning that wall of severity-colored noise into the five things that actually matter this week.

The trick is to stop reading findings as a flat list and start reading them as attack paths. One internet-exposed VM is a finding. One internet-exposed VM with a known CVE, holding a token to a role that can read the customer database, is an attack path. The second one is what you fix today. Modern CNAPP tools can compute this; insist on it and triage by reachable blast radius, not raw CVSS.

Anti-pattern Triaging cloud findings purely by CVSS score. A 9.8 on an isolated host with no sensitive access is less urgent than a 6.5 on the box that can reach your crown jewels. Severity without reachability and blast radius is just a number that makes dashboards look busy.

How I actually triage ten thousand findings

The first time a CNAPP lights up, the instinct is to sort by severity and start at the top. That is how teams burn a quarter fixing critical findings on assets nobody can reach while the real attack path sits at medium. The triage that works asks three questions in order, and a finding has to clear all three to jump the queue. Is it reachable from somewhere an attacker actually is, usually the internet or a low-trust zone. Does the affected thing hold or can it reach something sensitive, real data or a powerful identity. And is it exploitable in practice, not just theoretically present. A finding that is reachable, sensitive, and exploitable is a five-alarm fire regardless of its CVSS number. A critical CVE that fails any of the three can wait for the patch cycle.

The reason this works is that attackers do not think in findings, they think in paths. They chain a foothold to a credential to a permission to a data store. The job of a modern CNAPP is to compute those chains for you, and the job of the human is to break the chain at its cheapest link. Often that is not patching the exposed box at all, it is removing the over-broad permission three hops in, which kills a dozen paths at once.

read findings as a path, not a list (illustrative graph query)
> MATCH path = (e:Exposed {internet:true})
        -[:RUNS]->(w:Workload)
        -[:ASSUMES]->(r:Role)
        -[:CAN_READ]->(d:DataStore {sensitivity:'high'})
  WHERE w.has_known_cve = true
  RETURN path LIMIT 5
web-edge-02 -[runs]-> api-svc -[assumes]-> data-reader -[reads]-> customers-db
# one internet box, two hops, your customer data. fix the hop,
# not just the box. removing data-reader from api-svc kills it.

Kubernetes runtime reality

Kubernetes is where cloud security gets genuinely hard, because the cluster is a second cloud running inside your cloud, with its own identity system, network, and admission control. Three things earn their keep before anything fancy.

One: kill privileged and root containers. A container running as root with host mounts is one escape from owning the node. Enforce it with a policy engine at admission so it is impossible, not merely discouraged.

find running pods that are privileged or root
$ kubectl get pods -A -o json | jq -r '
  .items[] | select(
    .spec.containers[].securityContext.privileged == true or
    .spec.containers[].securityContext.runAsNonRoot != true
  ) | "\(.metadata.namespace)/\(.metadata.name)"' | sort -u
payments/legacy-batch-7f9c   # privileged: true
default/debug-shell         # someone left this here
$ # then enforce so new ones cannot be created:
admission policy: deny privileged pods (Kyverno)
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata: { name: disallow-privileged }
spec:
  validationFailureAction: Enforce
  rules:
  - name: no-privileged
    match: { any: [{ resources: { kinds: [Pod] } }] }
    validate:
      message: "privileged containers are not allowed"
      pattern:
        spec:
          containers:
          - securityContext:
              privileged: "false"

Two: default-deny network policy. Out of the box, every pod can talk to every other pod. That is flat-network east-west all over again, just inside the cluster. Three: runtime detection. Watch for the syscalls that mean someone is doing something they should not, like a shell spawning inside a container that should only ever run a single process.

The mistakes that actually get clusters owned

In practice, the cluster compromises I have seen did not come from exotic Kubernetes CVEs. They came from boring identity and boundary mistakes. The big one is the over-permissioned service account: a pod with a token mounted that can talk to the API server with far more rights than the app needs, so when the app is popped, the attacker inherits cluster power. By default Kubernetes mounts a service account token into every pod whether the app uses it or not, which is free credential material for anyone who lands code execution.

The second is treating the control plane and the workloads as one trust zone. The cluster is multi-tenant infrastructure even if you think of it as one app's home, and a container escape should not equal cluster admin. The third is forgetting that the cloud IAM layer and the Kubernetes RBAC layer are two separate permission systems that meet at the workload-identity boundary, and an attacker who pivots from one to the other often finds the join carelessly broad.

stop auto-mounting tokens where the app does not need them
$ # find pods that have the API token mounted but probably don't use it
$ kubectl get pods -A -o json | jq -r '
  .items[] | select(.spec.automountServiceAccountToken != false)
  | "\(.metadata.namespace)/\(.metadata.name)"' | head
frontend/web-7d9   (token mounted; static site, needs no API access)
$ # set automountServiceAccountToken: false on the SA or pod spec
  one less credential for an attacker to pick up on escape
Two permission systems, one boundary Cloud IAM and Kubernetes RBAC are different worlds with different models, and the place they connect, your workload identity binding, is where the dangerous over-grant usually hides. Audit that join specifically. A pod's Kubernetes RBAC might be tight while its bound cloud role can read every bucket in the account. The attacker does not care which system granted the access; they care that the path exists.
// 06

Secrets that do not leak

The leaked secret is the most boring and most common cloud breach vector, and it is almost entirely preventable. Two rules. Never put a secret in code, config, or an environment variable that lands in an image. Use a managed secrets store and fetch at runtime. And scan your git history, because the secret you rotated is still sitting in commit 4a3f from last spring.

scan a repo and its full history for secrets
$ gitleaks detect --source . --redact -v
Finding:     AWS Access Key
Secret:      AKIA****************
File:        deploy/old_config.py
Commit:      4a3f9c2  (2025-04-11)
leaks found: 1
$ # rotate the key NOW, then purge history; rotation first, always

Prefer short-lived credentials over stored ones entirely. Workload identity federation lets a CI job or a pod assume a cloud role with a token that lives for minutes, so there is no long-lived key to leak in the first place. That is the real fix; secret scanning is the safety net under it.

Cloud incident response, when it goes wrong anyway

When something does happen in cloud, the moves are different from on-prem. You rarely pull a network cable. You isolate by changing API permissions and snapshotting evidence before anything is destroyed. The first instinct of a panicking engineer, to terminate the compromised instance, is usually wrong, because it destroys the forensic evidence.

aws // contain a compromised instance without destroying evidence
$ # 1. snapshot the disk for forensics BEFORE touching anything
$ aws ec2 create-snapshot --volume-id vol-0abc \
  --description "IR-2026-06-forensic" --tag-specifications \
  'ResourceType=snapshot,Tags=[{Key=incident,Value=IR-2026-06}]'
SnapshotId: snap-0def  State: pending

$ # 2. isolate with a quarantine security group (deny all)
$ aws ec2 modify-instance-attribute --instance-id i-0abc \
  --groups sg-quarantine
  instance isolated, still running for memory capture

$ # 3. revoke the instance role's sessions (cut the token's power)
$ aws iam put-role-policy --role-name app-role \
  --policy-name revoke-now --policy-document file://deny-all.json
  standing sessions for that role now denied
Pre-write the runbook The middle of an incident is the worst time to figure out the AWS CLI flags for snapshotting a volume. Write and rehearse these runbooks in a game day before you need them. The teams that recover fast are the ones who have done it on a calm Tuesday afternoon already.

The shared-responsibility line, and where teams fall off it

Every cloud provider hands you a shared-responsibility diagram, and almost everyone nods at it without internalizing the one thing that matters: the line moves depending on which service you use, and the most expensive mistakes happen where a team assumes the provider has them covered when it does not. The provider secures the cloud. You secure what you put in it. Simple to say, constantly misread in practice.

The misreads cluster in predictable places. With managed databases, people assume the provider handles access control because it handles patching and uptime; it does not, the public-exposure setting and the IAM around it are yours. With serverless, people assume there is nothing to secure because there is no server; the function's permissions, dependencies, and the data it touches are all yours. With managed Kubernetes, the provider runs the control plane but every workload, network policy, and RBAC binding is yours. The pattern is always the same: the more managed the service feels, the more tempting it is to assume security came bundled, and the more surprised the team is at the breach review.

Service typeProvider handlesYou still own (where breaches happen)
IaaS (VMs)Hypervisor, physical, network fabricOS patching, firewall rules, IAM, data
Managed DBPatching, backups, uptimePublic exposure, access control, encryption choices
ServerlessRuntime, scaling, hostFunction permissions, dependencies, input validation
Managed K8sControl plane availabilityWorkloads, RBAC, network policy, node config
SaaSAlmost everything technicalYour configuration, your data, who you grant access

Multi-cloud multiplies the line, it does not average it

Running three clouds does not give you one shared-responsibility model, it gives you three, each drawn slightly differently, plus the cognitive load of remembering which is which. The teams that handle multi-cloud well do not try to master each provider's quirks equally. They define their own security baseline in provider-neutral terms, the outcomes they require regardless of cloud, then map each cloud's specific controls up to that baseline. Encrypt sensitive data at rest is the requirement; the specific service and flag that achieves it differs per cloud and is an implementation detail. That inversion, requirements first and provider controls second, is what keeps a multi-cloud program coherent instead of three disconnected silos that each think the others have it handled.

The "I thought the cloud did that" breach The single most common cloud breach narrative in post-mortems is some version of "we assumed the provider handled it." A storage bucket left public because someone thought the default was private. A database reachable from the internet because uptime was managed so surely security was too. Read the responsibility line for every service you adopt, out loud, in the design review. The provider will not save you from a door you opened yourself, and their diagram already told you it was your door.
// 09

The short version

If you do nothing else across your three clouds, do these. Shrink identity blast radius by hunting wildcard permissions and killing standing service-account keys. Put hard guardrails at the org level so the dangerous config is impossible, not merely flagged. Scan IaC before merge and git history for secrets, and move to short-lived credentials so there is less to leak. Treat your control-plane logs as the security camera they are, and pre-write your IR runbooks.

None of this is exotic. The exotic stuff almost never gets you. The propped-open door does.
