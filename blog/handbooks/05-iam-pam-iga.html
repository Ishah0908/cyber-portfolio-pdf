Identity, Privilege & Governance at Scale

Identity is the control plane for everything now. Here is how I think about the joiner-mover-leaver lifecycle, separation of duties, privileged session governance, and the audit trail that keeps you out of trouble, across cloud and a hundred SaaS apps.

// 01

The three letters, untangled

People use IAM, PAM, and IGA interchangeably and then wonder why projects stall. They are different jobs. IAM is authentication and authorization: proving who you are and what you can access. PAM is the special handling of powerful accounts: vaulting, brokering, and recording privileged access. IGA is governance: the lifecycle, the access reviews, the certification that you can prove to an auditor that access is correct.

The way I hold it: IAM is the lock, PAM is the safe inside the building for the crown jewels, and IGA is the paperwork and review process that proves every key is in the right hands. You need all three, and they have to talk to each other.

The leverage point In a multi-cloud, multi-SaaS world, the identity provider is the universal control plane. Every app federates to it. That makes the IdP both your biggest security win (fix access once, fix it everywhere) and your biggest single point of failure (own the IdP, own everything). Govern it accordingly.
// 02

Joiner, mover, leaver: automate the lifecycle

Most access problems trace back to a broken lifecycle. Someone joined and got access cloned from a colleague. They moved teams and kept the old access on top of the new (privilege creep). They left and an account lingered for months. Each of these is a breach waiting to happen, and each is fixable with automation driven from an authoritative source, usually the HR system.

The mover transition is the silent killer. A grant-on-move without a corresponding revoke means people accumulate entitlements for a decade. Audit for it directly: find accounts whose access spans roles they no longer hold.

find likely leaver accounts that were never disabled (Entra)
PS> Get-MgUser -All -Property DisplayName,AccountEnabled,SignInActivity |
  Where-Object {
    $_.AccountEnabled -eq $true -and
    $_.SignInActivity.LastSignInDateTime -lt (Get-Date).AddDays(-90)
  } | Select DisplayName, @{n='LastSignIn';
       e={$_.SignInActivity.LastSignInDateTime}}
DisplayName        LastSignIn
Contractor A       2026-01-04   (enabled, silent 5 months)
Former Employee B  2025-11-20   (enabled, gone since Nov)
# enabled accounts with no recent sign-in = deprovisioning gap

Separation of duties

Separation of duties is the control that stops one person from holding a toxic combination of permissions, the classic being someone who can both create a vendor and approve payments to it. SoD is a governance model, not a technical toggle: you define the conflicting pairs, then continuously check that no identity holds both.

Conflict (toxic pair)Why it mattersControl
Create vendor + approve paymentInvoice fraudRequire different people; alert on overlap
Write code + approve own deploy to prodUnreviewed changeMandatory separate approver in pipeline
Grant access + audit accessCover own tracksReviewer cannot be the granter
Manage backups + manage encryption keysRansom + destroy recoverySplit duties across roles
SoD is continuous, not one-time Checking SoD at access-grant time is necessary but not sufficient. Conflicts accumulate as people move roles. Run the toxic-pair check continuously and surface violations for review, because the dangerous combination is usually assembled gradually, one innocent-looking grant at a time.

Privileged access and session governance

Privileged accounts are the keys to the kingdom, so they get special handling that normal accounts do not. The PAM model has three pillars. Vault the credentials so no human knows the actual admin password and it rotates automatically. Broker the access so admins connect through a gateway rather than directly, with just-in-time elevation. Record the session so there is an auditable trail of what was done with that power.

Combined with the just-in-time model from Zero Trust, this means a privileged session is requested, approved, time-boxed, fully recorded, and the credential never leaves the vault. A stolen laptop yields no standing admin power because there is none to steal.

audit // privileged role activations in the last 24h (should be rare, JIT)
kql> AuditLogs
| where TimeGenerated > ago(24h)
| where OperationName has "Add member to role"
| where Result == "success"
| project TimeGenerated, Initiator=InitiatedBy.user.userPrincipalName,
          Role=TargetResources[0].displayName
TimeGenerated      Initiator           Role
06-01 09:14        admin1@corp         Global Administrator  (JIT, 1h)
06-01 03:02        svc-automation      Global Administrator  
# a service account self-elevating to GA at 3am: investigate now
// 05

Phishing-resistant MFA, end to end

This bears repeating across every identity handbook because it is the single highest-impact identity control of the decade. Push-approval and SMS MFA fall to push fatigue and SIM swaps, both commodity attacks now. The bar is FIDO2 security keys or platform passkeys, which are bound to the legitimate origin so a phishing proxy cannot relay them. Roll to admins first (they are the highest-value target), then privileged and sensitive roles, then everyone. Track coverage weighted by privilege, because an admin still on SMS is far more dangerous than an intern on SMS.

Why ordinary MFA stopped being enough

It is worth being precise about what killed plain MFA, because the failure is not theoretical. The dominant credential attack now is adversary-in-the-middle phishing: the victim lands on a proxy that perfectly mirrors the real login page, enters their password and approves the MFA prompt, and the proxy relays all of it to the real site in real time and steals the resulting session token. The victim sees a normal login. The attacker walks away with an authenticated session, having defeated the password and the MFA in one motion. Kits that do this are rented cheaply and require little skill to operate.

The reason FIDO2 and passkeys defeat this is elegant: the credential is cryptographically bound to the real site's origin, so when the victim is on the phishing proxy, the authenticator simply refuses to produce a valid response for the wrong domain. There is nothing for the proxy to relay. This is not a marginal improvement over push MFA, it is a categorical one, because it removes the human's ability to be tricked into authenticating to the wrong place. That is why "we have MFA" is no longer the right answer to "are we protected against phishing." The right question is whether your MFA is phishing-resistant, and for most orgs the honest answer is "only for the admins so far, and we are working down the list."

Token theft survives MFA entirely Even phishing-resistant MFA only protects the moment of authentication. Once a session token exists, an attacker who steals it from a compromised device can replay it without ever touching your MFA. This is why the session layer matters: short token lifetimes, binding tokens to the device they were issued to, and continuous re-evaluation so a token used from a new location or an unhealthy device gets challenged again. MFA gets you a good login. It does not keep the session honest afterward. That job belongs to the continuous-evaluation side of Zero Trust.

Identity detection use-cases

Identity is now a primary detection surface. The behaviors worth alerting on, in rough priority order: a dormant account suddenly active, impossible travel (two logins too far apart in time and space to be real), privileged role granted outside the JIT process, MFA method registered then immediately used from a new device (a classic account-takeover pattern), and consent granted to a new OAuth application requesting broad scopes.

detect // risky OAuth consent grant (token-theft path)
kql> AuditLogs
| where OperationName == "Consent to application"
| extend scopes = tostring(TargetResources[0].modifiedProperties)
| where scopes has_any ("Mail.Read","Files.ReadWrite.All","offline_access")
| project TimeGenerated, User=InitiatedBy.user.userPrincipalName, scopes
TimeGenerated   User           scopes
06-01 11:40     jdoe@corp      Mail.Read, offline_access, Files.ReadWrite.All
# a user just gave an unknown app persistent access to their mail
# and all files. illicit consent grant is the modern phish.
// 07

The audit you will face

Sooner or later an auditor asks: prove that every person with access to this sensitive system should have it, and show me you reviewed it. That is the access certification, and IGA exists largely to make answering it possible. The two things that make audits painless: entitlements are tied to roles (so you certify a role once, not a thousand individual grants), and reviews are scheduled, tracked, and actioned (a review where everyone clicks "approve all" is theater the auditor will see through).

Make revocation the easy path The reason access reviews become rubber-stamp exercises is that revoking is scary (might break something) while approving is safe. Flip that. Make revocation low-risk and reversible, give reviewers usage data ("this person has not used this access in 6 months"), and the reviews start actually removing access. A review that never revokes anything is not a control.
// 08

The identities that are not people

Every control discussed so far implicitly assumes a human: someone to enroll in MFA, someone to certify in a review, someone whose joiner-mover-leaver you can drive from HR. But the fastest-growing population of identities in your estate has no human attached at all. Service accounts, API keys, OAuth applications, CI/CD tokens, cloud workload identities, bots. They now outnumber human identities many times over, and almost none of your human-centric governance reaches them.

This is the gap that keeps getting orgs breached after they have done the human side well. You can have flawless phishing-resistant MFA across every employee and still get fully compromised through a single OAuth application with standing access to everyone's mail, or a CI token with permanent production rights sitting in a pipeline variable. The attacker does not need to phish anyone if there is a non-human identity that already holds the keys and never gets reviewed.

find OAuth apps with broad standing permissions (Entra)
PS> Get-MgServicePrincipal -All |
  ForEach-Object {
    $perms = Get-MgServicePrincipalAppRoleAssignment -ServicePrincipalId $_.Id
    if ($perms.AppRoleId) {
      [pscustomobject]@{ App=$_.DisplayName; Grants=$perms.Count }
    }
  } | Sort-Object Grants -Descending | Select -First 10
App                       Grants
LegacyReportingConnector  23   # 23 app permissions, owner unknown
MarketingAutomation       11
# every high-grant app is a non-human identity to govern or kill

Govern machines like you govern people

The fix is to extend the same disciplines you already built for humans to the non-human population. Every machine identity needs an owner, a human who is accountable for its existence and answers for it in reviews. It needs a lifecycle, so that when the project or integration it served ends, it is deprovisioned rather than left to linger with live access. It needs least privilege, scoped to what it actually calls rather than the broad grant someone gave it to unblock a deadline. And wherever the platform allows, it needs to move off long-lived static secrets onto short-lived, federated credentials, so there is nothing durable to steal.

The ownerless token is the time bomb The most dangerous identity in most estates is a non-human one created years ago for a since-forgotten purpose, still holding production access, that no current employee can explain. Run a recurring sweep for machine identities with broad permissions and no recent activity or no named owner. An unowned, over-permissioned, unused credential is not a loose end to tidy up someday. It is an open door, and the only question is whether you find it before someone else does.
// 09

First principles

If identity is the control plane, then governing it well is most of security. Drive the lifecycle from an authoritative source so access tracks reality. Hunt the mover gap and the leaver gap, because that is where stale privilege hides. Vault, broker, and record privileged access so there is no standing power to steal and a clean trail of what was done. Put everyone on phishing-resistant MFA, admins first. And treat the audit as a forcing function for the hygiene you should be doing anyway.

Do this and the rest of your security program stands on solid ground. Skip it and you are defending a building where the locks are decorative.
